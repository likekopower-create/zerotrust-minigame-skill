คู่มือพัฒนามินิเกมสำหรับ ZERO TRUST SIMULATOR

เอกสารส่งมอบสำหรับผู้พัฒนาและ AI ที่ไม่มีซอร์สของ Simulation

ฉบับ 1.0 วันที่ 30 ตุลาคม 2026

คู่มือนี้กำหนดไฟล์ที่ต้องส่ง วิธีสร้างเกมเว็บที่เล่นแยกได้ วิธีทดสอบกับโฮสต์จำลอง และข้อตกลงส่งผลการเล่นกลับเข้า Simulation ผู้รับสามารถใช้ชุด Developer Kit นี้เริ่มงานได้โดยไม่ต้องมีตัวเกมหลัก บัญชี Google หรือคีย์ Supabase

ข้อสรุปสำคัญ เกมใหม่ต้องเล่นได้เองและรายงานผลจบหนึ่งครั้งต่อรอบ ระบบหลักเป็นผู้ตรวจผลและตัดสินคะแนนที่ได้รับ การทดสอบกับโฮสต์จำลองไม่ใช่การบันทึกคะแนนจริง โปรโตคอลสำหรับเกมภายนอกที่เสนอในคู่มือนี้ยังต้องเพิ่มตัวรับใน Simulation ก่อนนำเกมเข้าระบบจริง

1 ขอบเขตและสถานะระบบปัจจุบัน

ตรวจจากไฟล์ในเครื่องของ Simulation V0.0.3 หลังแยก Tetris วันที่ 30 ตุลาคม 2026 ไม่ใช่การรับรองว่า GitHub ที่เผยแพร่อยู่มีไฟล์ชุดเดียวกันทั้งหมด

ส่วนสถานะหน้าที่
Mini-Games/screen.jsมีแล้วในเครื่องหน้ารวมมินิเกมและหน้าจอ Tetris
Mini-Games/tetris/engine.jsมีแล้วในเครื่องกติกา Canvas ปุ่ม คีย์บอร์ด และสถานะเกม
Mini-Games/tetris/style.cssมีแล้วในเครื่องรูปแบบหน้าจอเกมและคลังมินิเกม
PlayerStatsManagerมีแล้วในระบบหลักเพิ่มคะแนน สถิติ และประวัติ
Cloud Sync และ Rankingมีแล้วในระบบหลักซิงก์ข้อมูลและอ่านอันดับ
zt-minigame/1ข้อกำหนดใหม่ในชุดนี้รูปแบบเชื่อมเกมภายนอกผ่านข้อความ
ตัวรับเกมภายนอกใน Simulationยังต้องพัฒนาตรวจข้อความ แปลงคะแนน และบันทึก

Tetris ปัจจุบันเป็นโมดูลที่ใช้ DOM ร่วมกับ Simulation ไม่ใช่เกม standalone และยังไม่ได้ย้ายเข้า iframe การย้ายไฟล์ไม่ได้ทำให้เกมภายนอกเสียบเข้าได้อัตโนมัติ คู่มือนี้เสนอเส้นทางสำหรับเกมใหม่ โดยไม่เปลี่ยนวิธีส่งคะแนนของ Tetris เดิม

ตำแหน่งอ้างอิงในเครื่องเจ้าของโครงการคือ D:\ZERO TRUST SIMULATOR\ZERO TRUST SIMULATOR.V0.0.3\ZERO TRUST SIMULATOR ส่วนผู้พัฒนาภายนอกไม่จำเป็นต้องมีตำแหน่งนี้ และห้าม hardcode เส้นทางนี้ในเกม

2 แบ่งหน้าที่ระหว่างเกมและระบบหลัก

ผู้พัฒนาเกมรับผิดชอบภาพ เสียง กติกา การควบคุม เงื่อนไขจบ คะแนนดิบ และการพักทรัพยากรของเกม ส่วนผู้ดูแล Simulation รับผิดชอบบัญชีผู้เล่น กฎรางวัล การยอมรับผล การบันทึกจริง การจัดอันดับ และการเชื่อมฐานข้อมูล

เรื่องเกมภายนอกSimulation
เข้าสู่ระบบ Googleไม่ทำจัดการบัญชี
คะแนนดิบในรอบคำนวณและส่งตรวจความสมเหตุสมผล
คะแนนที่ใช้จัดอันดับไม่กำหนดเองคำนวณตามกฎที่อนุมัติ
Supabase และ session ผู้เล่นไม่รับคีย์หรือ tokenจัดการสิทธิ์และข้อมูล
ออก พัก และเล่นต่อหยุดเวลา input และเสียงส่งคำสั่งและปิด iframe
เปิดเล่นโดยไม่มีโฮสต์เล่นฝึกได้ไม่มีการบันทึกจริง

การฝังเกมด้วย iframe ช่วยแยกหน้าและวงจรการทำงาน แต่ถ้าอยู่ origin เดียวกันไม่ได้หมายความว่าแยกสิทธิ์อย่างปลอดภัยจากโค้ดที่ไม่เชื่อถือ ต้องตรวจซอร์สและ dependency ก่อนรับเข้า หากใช้เกมที่ไม่เชื่อถือ ให้ผู้ออกแบบระบบแยก origin และกำหนด sandbox โดยไม่ลดมาตรการเพียงเพื่อให้เกมเปิดได้

3 โครงสร้างไฟล์ที่ต้องส่ง

โครงสร้างเกมหนึ่งเกมที่แนะนำมีดังนี้ ชื่อโฟลเดอร์และ gameId ใช้อักษรอังกฤษตัวเล็ก ตัวเลข และขีดกลาง เช่น scam-quiz หลีกเลี่ยงช่องว่างและชื่อซ้ำกับเกมเดิม

scam-quiz/
  index.html
  manifest.json
  game.js
  sdk.js
  style.css
  assets/
    icon.png
    images/
    audio/
  HANDOFF.md
ไฟล์ต้องมีหรือไม่รายละเอียด
index.htmlต้องมีหน้าเริ่มต้นที่เปิดตรงได้
manifest.jsonต้องมีรหัสเกม version entry protocol และช่วงคะแนนดิบ
game.jsต้องมีหรือไฟล์ bundle เทียบเท่ากติกาและ lifecycle ของเกม
sdk.jsต้องมีหรือ implementation เทียบเท่าhandshake ส่งผล และรับคำสั่ง
style.cssต้องมีหรือ CSS ที่รวมใน buildรองรับมือถือและพื้นที่ iframe
assetsตามการใช้งานส่งทรัพยากรครบพร้อมสิทธิ์ใช้งาน
HANDOFF.mdต้องมีวิธีรัน กติกาคะแนน dependency และผลทดสอบ

ถ้าใช้ Unity หรือ Godot ให้ส่ง Web Export ที่ build แล้ว พร้อมไฟล์ runtime, data และ wasm ที่อ้างอิงครบ แจ้งข้อกำหนด MIME, compression, WebGL และ header เพิ่มเติมให้ integrator ทราบ ไม่รับ .exe หรือ .apk เป็น entry ของ iframe การรองรับ Web Export แต่ละ engine ต้องทดสอบแยกจาก starter HTML นี้

ใช้เส้นทาง relative เช่น assets/audio/click.mp3 หลีกเลี่ยง /assets เพราะจะชี้ไปที่รากโดเมนและอาจหลุดจาก path repository ของ GitHub Pages ตัวพิมพ์เล็กใหญ่ในชื่อไฟล์และ URL ต้องตรงกัน ห้ามอ้าง D:\ หรือ localhost จาก build ส่งมอบ

4 รายละเอียด manifest และข้อมูลที่ต้องตกลง

manifest ใช้บอกคุณสมบัติของเกม ไม่ใช่หลักฐานว่าเกมได้รับสิทธิ์ให้คะแนนแล้ว ผู้ดูแลต้องเพิ่มเกมใน registry ฝั่ง host โดยตรวจค่าที่ได้รับ ไม่ fetch แล้วเชื่อ rewardProposal โดยอัตโนมัติ

{
  "id": "tap-training",
  "title": "Tap Training Demo",
  "version": "1.0.0",
  "protocol": "zt-minigame/1",
  "entry": "index.html",
  "orientation": "any",
  "score": {
    "kind": "final",
    "rawMin": 0,
    "rawMax": 50
  },
  "dependencies": []
}

ก่อนทำเกมให้ตกลงชื่อเกม กลุ่มผู้เล่น ภาษา รูปแบบการควบคุม เงื่อนไขชนะหรือแพ้ เวลาเฉลี่ยต่อรอบ จำนวนคะแนนดิบสูงสุด และนโยบายเล่นซ้ำ ถ้ายังไม่ตกลงรางวัล ให้ระบุว่าเป็นข้อเสนอ ห้ามสมมติว่าเกมใหม่ทุกเกมได้ 20 คะแนนตาม BlockTown

kind final หมายถึงส่งคะแนนดิบสุดท้ายของรอบ ไม่ใช่ส่งแต้มสะสมบัญชี ไม่ใช่ส่งทุก frame และไม่ใช่ส่ง delta ซ้ำระหว่างรอบเดียวกัน ถ้าเกมต้องส่ง progress ระหว่างเล่น ให้แยกเป็นข้อความเพื่อแสดง UI โดยไม่เพิ่มคะแนนจนกว่าจะมีกฎรองรับ

5 สถานะเกมและการเล่นแยก

เกมควรมีสถานะ loading, ready, playing, paused, finished และ stopped โดยเก็บการเปลี่ยนสถานะชัดเจน ปุ่มเล่นต้องไม่เริ่มสอง loop พร้อมกัน และ input หลัง finished ต้องไม่เพิ่มคะแนน

เปิด index.html โดยตรงผ่าน HTTP คือโหมดฝึก เกมเริ่มได้เองโดยไม่มี window.parent ที่ต่างจากตัวเอง แสดงข้อความว่าไม่บันทึกคะแนนจริง และเล่นซ้ำได้ภายในเกม ไม่สร้างบัญชีหรือเรียก API เพื่อจำลองว่าบันทึกแล้ว

เมื่ออยู่ใน iframe เกมรอ init จากโฮสต์ก่อนเริ่มรอบ ใช้ runId ใหม่เมื่อโฮสต์อนุญาต replay เก็บเวลาและคะแนนเฉพาะรอบนั้น เมื่อมี pause ให้หยุดเวลาเกม ฟิสิกส์ input และเสียง โดยเก็บสถานะไว้ resume จึงเล่นต่อได้ ส่วน stop ต้องยกเลิก timer, requestAnimationFrame, event listener ที่ไม่ใช้ และเสียงทั้งหมด

หากแท็บถูกซ่อน ให้พักเกมทันที การกลับมาเห็นแท็บไม่ควรข้ามหน้าพักโดยไม่ตั้งใจ โฮสต์ตัวอย่างให้ผู้ทดสอบกดเล่นต่อเอง สำหรับเกมจริงให้มีปุ่มเล่นต่อหรือการจัดการ resume ที่ตรงกันทั้งสองฝั่ง

บนมือถือให้ใช้พื้นที่ของ iframe เป็นขนาดจริง ไม่อ้างเฉพาะขนาดหน้าจอ desktop ทดสอบ 320 × 568, 390 × 844, 844 × 390 และการปรับขนาดระหว่างเล่น ไม่ยืด Canvas จนตำแหน่งสัมผัสคลาดเคลื่อน ปุ่มสำคัญควรมีพื้นที่แตะอย่างน้อย 44 × 44 CSS px เป็นเกณฑ์ออกแบบของชุดนี้ และมีสถานะ focus ที่มองเห็น

6 ข้อตกลงข้อความสำหรับเกมภายนอก

ชื่อสัญญาคือ zt-minigame/1 รูปแบบทุกข้อความใช้ object ที่ส่งผ่าน postMessage ห้ามส่ง JSON string แทน object ห้ามส่ง HTML ให้โฮสต์แสดงด้วย innerHTML และไม่ส่งข้อมูลบัญชีผู้เล่น

ฟิลด์ชนิดข้อกำหนด
channelstringต้องเป็น zt-minigame
versionintegerต้องเป็น 1
typestringชนิดข้อความตามตารางถัดไป
gameIdstringต้องตรง registry และ manifest
sessionIdstring หรือ nullhost ออกให้เมื่อเปิดเกม
runIdstring หรือ nullhost ออกให้แต่ละรอบ
eventIdstringUUID ของเหตุการณ์ ส่งซ้ำใช้ค่าเดิม
payloadobjectข้อมูลเฉพาะชนิด ไม่ใส่ secret

ready ก่อน handshake ใช้ sessionId และ runId เป็น null ได้ ส่วน init และทุกข้อความหลัง init ต้องตรงกับ session และรอบที่เปิดอยู่ hostOrigin ใน query คือ origin ที่อนุญาต เช่น https://example.com ไม่มี path ไม่ใช่ URL ของหน้า Simulation ทั้งเส้น

ทิศทางtypeความหมาย
เกมไป hostreadyเกมพร้อม ขอเริ่ม handshake
host ไปเกมinitส่ง sessionId runId และ locale
เกมไป hostresultส่งผลสุดท้ายหนึ่งชุดต่อรอบ
host ไปเกมackยอมรับหรือปฏิเสธ result
host ไปเกมpause resume stopจัดการ lifecycle
เกมไป hostreplay-requestขอรอบใหม่ รอ init ใหม่

ลำดับปกติคือ host สร้าง iframe → เกมส่ง ready → host ส่ง init → เกมเริ่มเล่น → เกมส่ง result → host ตรวจและบันทึก → host ตอบ ack เกมจึงแสดงผลรับรองจาก host โดยไม่ตีความว่า ack ทุกชนิดหมายถึงบันทึกออนไลน์แล้ว

โฮสต์ต้องรับ ready ซ้ำและตอบ init ของรอบเดิมได้โดยไม่สร้างรอบใหม่ เกมต้องไม่รีเซ็ตเมื่อได้รับ init เดิมซ้ำ หากยังไม่มี init ให้แจ้งการเชื่อมต่อและให้ผู้ใช้ลองใหม่หรือกลับออกได้ SDK ตัวอย่างส่ง ready ทุก 1.5 วินาทีจนได้รับ init ผู้พัฒนาสามารถเพิ่ม timeout และ UI ลองใหม่ตามลักษณะเกมได้

7 รูปแบบผลการเล่นและการตอบรับ

ตัวอย่างนี้ใช้เกมเดโมแตะครบห้าครั้ง ได้คะแนนดิบ 50 กฎจำลองให้ 10 คะแนน ตัวเลขนี้เป็นกฎของเดโมเท่านั้น

{
  "channel": "zt-minigame",
  "version": 1,
  "type": "result",
  "gameId": "tap-training",
  "sessionId": "HOST_SESSION_UUID",
  "runId": "HOST_RUN_UUID",
  "eventId": "8cccd55d-6353-4c34-a0c0-49621856a99d",
  "payload": {
    "outcome": "completed",
    "rawScore": 50,
    "durationMs": 12000,
    "metrics": { "taps": 5 }
  }
}

outcome รับ completed, failed หรือ abandoned แต่ host เป็นผู้ตัดสินว่าแต่ละสถานะได้รับรางวัลหรือไม่ rawScore ต้องเป็นจำนวนเต็มปลอดภัย อยู่ในช่วงของเกม ไม่รับค่าติดลบ NaN, Infinity, string หรือตัวเลขเกินเพดาน durationMs คือเวลารอบหน่วยมิลลิวินาที metrics เป็นข้อมูลเฉพาะเกมที่ต้องกำหนด schema ไม่ใส่อีเมล ชื่อจริง หรือ token

ack ต้องสะท้อน gameId, sessionId, runId และ eventId ที่รับมา โดย payload ใช้ status accepted หรือ rejected และเหตุผลที่อ่านได้ เช่น INVALID_SCORE เกมต้องจับคู่ eventId ก่อนเปลี่ยนสถานะผลลัพธ์

{
  "status": "accepted",
  "awardedPoints": 10,
  "persisted": "mock-only"
}

payload ด้านบนเป็นของโฮสต์ทดสอบ persisted ในระบบจริงควรกำหนดเป็น local หรือ cloud ตามสิ่งที่สำเร็จจริง หากบันทึกเพียง local ห้ามแสดงว่าบันทึกออนไลน์สำเร็จ หากปฏิเสธให้ใช้ payload เช่น status rejected และ reason INVALID_SESSION

SDK ตัวอย่างส่ง result สูงสุดสามครั้ง ห่างกัน 1.8 วินาที ถ้ายังไม่มี ack จะแสดงปุ่มลองส่งผลเดิม ไม่สร้าง eventId ใหม่ ไม่เพิ่ม rawScore และไม่เปลี่ยน runId เพื่อหลบการส่งซ้ำ เมื่อผู้เล่นกด replay ต้องให้ host ออก runId ใหม่ก่อน

8 วิธีที่คะแนนเชื่อมกับระบบเดิม

ระบบเดิมใช้ localStorage key zerotrust_player_stats_v1 เก็บ missionScore, minigameScore, totalScore, counts และ history ฟังก์ชัน recordMinigameScore เพิ่ม points เข้า minigameScore คำนวณ totalScore ใหม่ แล้วเพิ่มประวัติ type minigame พร้อม game, points และ timestamp

window.PlayerStatsManager.recordMinigameScore(
  awardedDelta,
  approvedGameId
);

ฟังก์ชันนี้รับ delta ที่จะบวก ไม่ใช่ยอดรวม เช่นผู้เล่นมี minigameScore 100 และจบรอบใหม่ได้รางวัล 10 ให้ส่ง 10 เพื่อได้ 110 ห้ามส่ง 110 เพราะจะกลายเป็น 210 ตัวฟังก์ชันไม่มีการกันผลซ้ำและไม่ได้ตรวจความถูกต้องของกฎเกมให้ผู้เรียก

Tetris เดิมเรียก delta ระหว่าง soft drop, hard drop และเคลียร์แถว จึงต้องรักษาเส้นทางเดิมของ Tetris ไว้ อย่าเพิ่มตัวรับ result มาบวกซ้ำอีกรอบเมื่อ game over ส่วนเกมภายนอกตามสัญญานี้ให้ host เพิ่ม awardedDelta หลังยอมรับผลสุดท้ายหนึ่งครั้ง

เส้นทางข้อมูลจริงที่มีอยู่คือ PlayerStatsManager → saveStats → localStorage และ UI → Cloud Sync ตรวจ snapshot → ZeroTrustCloudData.save → RPC save_v003_player_data → v003_player_data ระบบ Ranking อ่านข้อมูลที่เกี่ยวข้องต่อผ่านระบบเดิม ไม่ควรให้แต่ละเกมสร้างฐานข้อมูลคะแนนของตัวเอง

Cloud Sync ใช้ p_stats, p_progression, p_blocktown_answers และ p_expected_revision การซิงก์ทำงานตามสถานะบัญชี การเลือกข้อมูล และ revision โดยตรวจเป็นช่วงประมาณ 2.5 วินาทีเมื่อพร้อม ไม่ได้รับประกันว่าผลเกมจะขึ้น cloud ทันทีที่เรียก recordMinigameScore หาก guest หรือออฟไลน์จะมีเพียงข้อมูลในเครื่องตามการทำงานเดิม

จำนวนผู้เล่นและคะแนนใน Player Atlas เป็นงานอ่านภาพรวมจากข้อมูลส่วนกลาง เกมภายนอกไม่ควรเขียนหรือสรุปข้อมูล Atlas โดยตรง และการเพิ่ม minigame ไม่ต้องแก้ Short Series หรือ BlockTown ถ้าไม่ได้เปลี่ยนกฎของระบบเหล่านั้น

9 การตรวจข้อความและป้องกันคะแนนซ้ำ

ทุก host ที่รับผลต้องตรวจ event.source ว่าตรง iframe.contentWindow และ event.origin ว่าตรง origin ของเกมที่อนุญาต ก่อนอ่าน payload ตามที่กำหนด ห้ามใช้แค่ gameId เป็นหลักฐาน และไม่ใช้ targetOrigin เป็น * สำหรับเกม HTTP ปกติ

จากนั้นตรวจ channel, version, type, gameId, sessionId, runId และ eventId ว่าตรง registry และรอบที่เปิดอยู่ ตรวจ schema และขนาดข้อมูลที่รับ จำกัดช่วงคะแนนและเวลา พร้อมปฏิเสธเกมที่ยังไม่ได้ลงทะเบียน การเชื่อมต่อใช้ HTTPS ใน production และ localhost สำหรับทดสอบ

กันซ้ำสองระดับ คือผล eventId เดิมต้องตอบ receipt เดิมโดยไม่เพิ่มคะแนน และผล eventId ใหม่แต่ runId เดิมที่จบแล้วต้องถูกปฏิเสธ ไม่ใช่นับเป็นอีกรอบ โฮสต์จำลองเก็บ receipt ในหน่วยความจำเท่านั้น รีเฟรชแล้วข้อมูลนี้หาย ไม่เหมาะกับคะแนนจริง

production ต้องมี transaction หรือ RPC ที่ทำการยอมรับผล เพิ่มคะแนน และบันทึก receipt อย่างเป็นอะตอม โดยมี unique key เช่น player_id ร่วมกับ game_id และ run_id รวมถึง event_id ที่ตรวจย้อนกลับได้ การแยกเพิ่มคะแนนกับบันทึก receipt คนละขั้นทำให้หน้าเด้งหรือเครือข่ายขาดแล้วเกิดคะแนนซ้ำหรือหายได้ ต้องไม่อ้างว่า localStorage บวกแล้วจะกันซ้ำข้ามอุปกรณ์ได้

sessionId และ runId ใน client ช่วยจับคู่รอบ แต่ไม่ใช่หลักฐานป้องกันโกง ผู้ใช้ยังแก้ JavaScript หรือปลอมผลได้ ถ้าใช้คะแนนจัดอันดับอย่างน่าเชื่อถือ ควรให้เซิร์ฟเวอร์ออก session ตรวจผลตามกติกาและจำกัดสิทธิ์ RPC ที่แก้คะแนน ไม่เชื่อข้อมูล client เพียงเพราะผ่าน origin check ส่วนรายละเอียดตารางและ migration ต้องออกแบบและทบทวนแยกก่อนใช้จริง

10 วิธีใช้ชุดตัวอย่างโดยไม่มี Simulation

ส่งโฟลเดอร์ zerotrust-minigame ทั้งชุดให้ผู้พัฒนา ภายใน assets/starter มีเกมเดโมและโฮสต์ทดสอบอยู่ครบ ไม่ต้องส่งซอร์ส Simulation และไม่ต้องส่งไฟล์ Supabase config

1. เปิด terminal ใน assets/starter แล้วรัน python -m http.server 8780 --bind 127.0.0.1 ถ้าไม่มี Python ใช้ static HTTP server ของเครื่องมือพัฒนาที่มีอยู่

2. เปิด http://127.0.0.1:8780/game/index.html เพื่อทดสอบ standalone ต้องแสดงว่าไม่บันทึกคะแนนจริง

3. เปิด http://127.0.0.1:8780/test-host.html เพื่อทดสอบแบบฝัง เมื่อแตะครบห้าครั้ง host แสดงคะแนนจำลอง 10

4. กดส่งผลล่าสุดซ้ำ คะแนนต้องยังเป็น 10 เปิดไม่ตอบรับผลเพื่อทดสอบ retry ทุกครั้งต้องเป็นผลเดิม ไม่บวกซ้ำ

5. กดเล่นใหม่ในเกม เมื่อโฮสต์ส่ง init รอบใหม่จึงเริ่มรอบใหม่ได้ จบรอบที่สองคะแนนจำลองรวมเป็น 20

6. ลองพัก เล่นต่อ ออก เปิดใหม่ และสลับแนวตั้งแนวนอน ปุ่มกลับของระบบจริงเป็นหน้าที่ integrator เพิ่มนอก iframe

host-rules.js มีเพดานคะแนนเฉพาะเดโม ต้องเปลี่ยนตามกฎเกมที่ตกลง พร้อมเปลี่ยน gameId ใน manifest, SDK และ registry ของ test host ให้ตรงกัน การเปลี่ยนเพียงชื่อเรื่องจะยังทำให้ระบบเข้าใจว่าเป็น tap-training

ไฟล์ที่ใช้ฝึกและโฮสต์จำลองมีสิทธิ์แค่ในเครื่อง ไม่มีการเพิ่มคะแนนจริง ไม่รวมเกมนี้ในหน้ารวม Simulation อัตโนมัติ และไม่มีคำสั่งอัปโหลดหรือ deploy ในชุดนี้

11 ขั้นตอนสำหรับผู้เชื่อมเข้าระบบหลัก

ขั้นตอนส่วนนี้เป็นงานที่ต้องทำภายหลังเมื่อรับเกมมา ไม่ใช่ความสามารถที่เพิ่มใน Simulation พร้อมเอกสารฉบับนี้ อ่านรายละเอียดเพิ่มเติมใน references/integration.md

1. ตรวจแพ็กเกจเกม แหล่งที่มาทรัพยากร dependency และความสามารถในการทำงานบน HTTP กับ iframe โดยไม่ใช้ parent DOM

2. วางเกมใน Mini-Games/รหัสเกม/ ที่อยู่ภายในโฟลเดอร์แอป Simulation หรือเลือกตำแหน่งกลางที่แก้ path ด้วย base URL ชัดเจน หากเปิดได้ทั้ง root และโฟลเดอร์ V0.0.3 ต้องทดสอบทั้งสองเส้นทาง

3. เพิ่ม game registry ที่ระบุ entry, allowedOrigin, version, score bounds, กฎรางวัล และ replay policy ที่อนุมัติ ค่าฝั่ง host เป็นผู้ตัดสิน ไม่ใช้ manifest จากเกมเป็นอำนาจอนุมัติ

4. เพิ่มหน้าฝัง iframe ในจอมือถือและปุ่มกลับ แล้วทำ handshake ตาม zt-minigame/1 ตั้ง source/origin check และ session/run lifecycle

5. เพิ่มผลตรวจ receipt และการแปลง rawScore เป็น awardedDelta สำหรับการทดสอบภายในเรียก PlayerStatsManager เพียงครั้งต่อผลที่ยอมรับ สำหรับ production ให้ทำเส้นทางตรวจและบันทึกบนเซิร์ฟเวอร์ก่อนอ้างความน่าเชื่อถือของอันดับ

6. เชื่อมสถานะสำเร็จ local กับสถานะ cloud แยกกัน ห้ามเขียนทับข้อมูลเมื่อ revision conflict ใช้ UI เลือกข้อมูลและระบบ sync เดิม

7. ทดสอบคะแนนก่อนและหลังทั้ง local, guest, offline, login, cloud conflict และ replay ตรวจไม่กระทบ Tetris ภารกิจ Settings BlockTown และ Atlas

ห้ามฝัง iframe ของเกมที่ไม่เชื่อถือแบบ same origin แล้วส่ง access token เข้าไป การเพิ่ม sandbox ต้องทดสอบ event.origin และ protocol ให้ตรงกัน SDK นี้รองรับ origin HTTP/HTTPS ชัดเจน ไม่รองรับ opaque origin null จาก sandbox ที่ไม่ให้ same origin โดยอัตโนมัติ

13 คำสั่งตัวอย่างสำหรับส่งให้ AI อีกตัว

คัดลอกข้อความต่อไปนี้ พร้อมแนบ Developer Kit ทั้งโฟลเดอร์ โดยแทนข้อความในวงเล็บให้ตรงงาน

พัฒนามินิเกม HTML5 ชื่อ [ชื่อเกม] รหัส [game-id] สำหรับ ZERO TRUST SIMULATOR โดยอ่าน SKILL.md และ references/developer-guide.md ก่อน เริ่มจาก assets/starter ให้เกมเล่นแยกได้โดยไม่ต้องมี Simulation และเล่นใน iframe ผ่าน zt-minigame/1 รองรับมือถือแนวตั้งแนวนอน ใช้ไฟล์ relative และไม่เรียก Supabase หรือแก้คะแนนส่วนกลางเอง

กติกาเกมคือ [รายละเอียด] เงื่อนไขจบคือ [รายละเอียด] คะแนนดิบอยู่ในช่วง [min ถึง max] รางวัลเข้า Simulation เป็นข้อเสนอที่ต้องตกลงกับผู้ดูแล ใช้ final result หนึ่งชุดต่อ runId และส่งซ้ำด้วย eventId เดิมเท่านั้น รับ pause resume stop และขอ replay โดยรอ init ใหม่ ห้ามเขียนว่าเชื่อมคะแนนจริงแล้วหากทดสอบเพียง mock

ส่งโฟลเดอร์เกมพร้อม index.html, manifest.json, JS, CSS, assets และ HANDOFF.md รวมผลทดสอบ standalone กับ mock host กรณีส่งซ้ำ คะแนนผิด และหมุนจอ ไม่ต้องมีตัวเกมหลัก และไม่ deploy งานโดยอัตโนมัติ
